# Admin /items error — Root Cause Report

Date: 2026-10-22
Trace: `c9b116f3-e8be-4b60-a826-115058122ff8` (shape matches backend `X-Request-Id` UUID)

## Root cause

Running backend JVM (PID 33928, started 2026-10-22 **14:13:30**) predates the reward module + Flyway V12/V13. Specifically:

- `src/main/resources/db/migration/V12__rewards_inventory.sql` created **15:12:36**
- `src/main/java/com/dauviet/reward/api/AdminItemController.java` created **15:17:44**
- `target/classes/com/dauviet/reward/api/AdminItemController.class` compiled **15:56:02**
- Flyway history stops at V11 (`installed_on = 14:13:33` — same boot that started the JVM)
- Postgres `\dt` confirms: no `item_catalog`, no `item_unlock_rule`, no `user_inventory`

So JVM was never restarted after reward code was added. The `/api/v1/admin/items` mapping is not registered in `DispatcherServlet`. When admin UI calls it:

1. `SecurityConfig` matcher `/api/v1/admin/**` passes (user has `CONTENT_ADMIN` role).
2. `DispatcherServlet` finds no handler → throws `NoResourceFoundException`.
3. `GlobalExceptionHandler.handleNoResource` → HTTP **404** `{code:"NOT_FOUND", message:"Resource not found", traceId:<uuid>}`.
4. Next.js proxy at `src/app/api/proxy/[...path]/route.ts` forwards body+status verbatim (filters only hop-by-hop/set-cookie headers).
5. Admin `toUserMessage` (`src/lib/api-error.ts:48-77`) has no `NOT_FOUND` mapping → `default:` → "Có lỗi xảy ra, vui lòng thử lại" + `traceId` shown.

The traceId `c9b116f3-...` in the UI was generated by backend `TraceIdFilter` (line 38-41: incoming header absent → `UUID.randomUUID()`).

**No backend code bug.** Two environmental gaps:

- JVM not restarted after compiling new controllers.
- DB migration V12/V13 not applied (would also fail even if restarted with current code — `item_catalog` missing ⇒ `ddl-auto: validate` would refuse to boot).

Backend endpoint actually intended (once code is running): `AdminItemController.list` at `dau-viet-backend/src/main/java/com/dauviet/reward/api/AdminItemController.java:42-50` — `GET /api/v1/admin/items` → `AdminItemService.list` → `ItemCatalogRepository.search` → `PageResponse<AdminItemResponse>`.

## Fix recommendations (in order)

1. **Apply pending migrations + restart backend** (highest priority, resolves the issue):
   - Stop JVM PID 33928.
   - Restart via `./mvnw spring-boot:run -Dspring-boot.run.profiles=local` (or whatever script is used). On boot Flyway applies V12 (`item_catalog`, `item_unlock_rule`, `user_inventory` + 8 seeded items + rules) and V13 (description updates). Then `ddl-auto: validate` succeeds because schema exists.
   - Verify: `docker exec dauviet-postgres psql -U dauviet -d dauviet -c "SELECT count(*) FROM item_catalog;"` → expect 8.

2. **Add `NOT_FOUND` mapping to admin `toUserMessage`** (`dau-viet-admin/src/lib/api-error.ts`):
   - Map `NOT_FOUND` → "Dữ liệu không tồn tại hoặc đã bị xoá" so 404s render meaningful text, not generic "Có lỗi xảy ra".
   - Optional: also map `INTERNAL_ERROR`, `PAYLOAD_TOO_LARGE`, `METHOD_NOT_ALLOWED` for completeness — they currently hit the same default.

3. **Surface upstream status code in ErrorState** (nice-to-have):
   - Show `err.status` alongside traceId so support can immediately distinguish 404 vs 500 without backend log access.

4. **Docs/runbook note**:
   - In `docs/backend-runbook.md` add reminder: after adding Flyway V* files + new `@RestController`, must restart the Spring Boot process — `target/classes` changes alone are not hot-loaded (no devtools in this project).

- The user pasted "backend log" with only startup events — is the dev actively tailing that JVM's stdout, or looking at a different log file? Worth confirming there's no second backend instance elsewhere.
- Should admin add `NOT_FOUND` and other unmapped codes to `toUserMessage`, or rely on the traceId for support? Current pattern suggests adding only common cases — adding `NOT_FOUND` seems minimum-sufficient.
